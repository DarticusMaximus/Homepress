# Stage 05: Cross-Run Deduplication — Summary

## What this stage delivered

The same topic no longer recurs across consecutive issues. Each new run now suppresses candidates that are semantically too close to topics from that newsletter's recent completed issues, so the operator's daily digest feels fresh even when the underlying feed sources keep covering the same story. The operator controls the lookback window per newsletter (default three recent completed issues, configurable zero to ten — zero turns cross-run suppression off for that newsletter) and tunes strictness through a single `.env` threshold (default `0.85`, range zero to one, no GUI). Suppressed candidates are visible on the Runs page: count, every suppressed title, and which prior issue it matched, so the filter is auditable without waiting for a future inspect UI.

The suppress happens **before** within-run diversity selection. Below-threshold candidates pass through unchanged; above-threshold candidates are hard-dropped and never reach MMR. The remaining pool still flows through the existing MMR selection, so the run still fills toward the newsletter's target item count — a short issue only happens when the remaining pool is genuinely exhausted (in which case the run is marked failed with "No articles selected", and the suppression record is still saved so the operator sees why). Embed failures during suppression are logged and degraded to a no-op; the run continues to MMR rather than failing on a transient provider blip.

A short hardening pass closed four quality findings from the stage review (one optimization for empty candidate sets, ten parser edge cases for the threshold env reader, five malformed-embedding defensive guards, and an empty-`matchedRunId` UI label that previously would have surfaced the literal `"run …"`). The repository formatting gate is also restored — every Prettier-selected maintained file is formatted, with the four intentional ignore entries (`output/`, legacy `newsletters.yaml`, `.cursor/`, `.opencode/`) confirmed excluded.

## How it maps to the plan

- **Stage Intent:** Stop the same topic recurring across consecutive issues by suppressing lookback-similar candidates before within-run diversity selection — so each issue feels fresh even when the day's firehose keeps repeating the same story. This serves the product's temporal-diversity goal and makes retained run history actively useful, not just an audit trail.
- **Acceptance criteria met:**
  - [x] Lookback defaults to 3 on new newsletters; the operator can change it per newsletter (including `0` = off); the value persists and reloads.
  - [x] With lookback ≥ 1 and at least one completed prior issue in range, a candidate whose embedding similarity to a lookback topic exceeds the env threshold is hard-dropped before MMR.
  - [x] With lookback `0`, or with no completed prior issues in range, selection behaves as it did before this stage (no suppressions).
  - [x] After suppression, MMR still fills toward the newsletter's target item count from remaining candidates; the run completes with a shorter selection only when the remaining pool is exhausted.
  - [x] A completed run's summary shows the suppression count, each suppressed title, and which prior issue it matched.
  - [x] The similarity threshold is read from a documented `.env` variable; changing it takes effect on the next run without editing application code.
  - [x] `pnpm format:check` exits zero without reporting maintained source, configuration, or documentation files.
- **North star link:** The product exists to condense an overwhelming daily firehose into a small, fresh, relevant digest. Stage 04 made runs observable and recoverable and guaranteed a stable floor of three completed runs per newsletter. This stage activates that retained history: it is now the substrate for cross-run temporal diversity, so consecutive issues stop repeating the same topic. Goal 8 ("avoid topic repetition across consecutive issues") is now satisfied end-to-end.

## What was built

- **Feature 01 — Lookback config:** A new `lookback` number attribute on the `newsletters` Appwrite collection (default `3`, range `0..10`, `0` = off). Exposed as a required number field in the newsletter create/edit dialog with a helper line explaining the off value. Read-path coerce ensures pre-existing newsletters behave as default-on without a data migration. Validation rejects out-of-range and non-integer values with the established `NewsletterRepositoryError("validation", …)` pattern. Form reuses the `newsItems`-style `parseOptionalInt` pattern; the update action deliberately uses `lookback ?? -1` (not `?? 0`) as the missing-field sentinel because zero is a valid value.
- **Feature 02 — Lookback topic load:** A shared, testable loader (`loadLookbackTopics`) returns the parsed `topicSummary` entries from a newsletter's latest N completed runs. `lookback ≤ 0` short-circuits to an empty result without calling Appwrite; completed-only filtering and the most-recent-first ordering (`endedAt || startedAt` desc, `$id` desc tie-break) match Stage 04's retention sort so the protected floor of three is honored. Malformed `topicSummary` JSON degrades per-run to empty topics without throwing into the caller.
- **Feature 03 — Pre-MMR semantic suppress:** Embeds lookback topics and candidates as **title + tags** (apples-to-apples), hard-drops any candidate whose max cosine similarity to a lookback topic is `>=` threshold, and persists a `suppressSummary` JSON on the run document. The run then runs the existing MMR (`selectDiverse`) on the survivors using its existing **title + body** embed. Threshold is read from `CROSS_RUN_SIMILARITY_THRESHOLD` (default `0.85`, clamped `[0,1]`). Empty pool after suppress fails selection cleanly; short survivors complete as under-target issues. Embed failures degrade to no-op suppress and log. The suppress runs on the full post-score array before MMR's `minScore` filter, so a candidate that would have been dropped by MMR still appears in the suppression record when applicable.
- **Feature 04 — Suppress visibility:** The Runs list gains a **Suppressed** column (after Failed feeds) on the table and a `Suppressed:` row on the card. Table shows a compact `N suppressed` label whose `title` attribute and visually-hidden list expose every item line (suppressed candidate title + matched prior issue). Card shows the same information as visible list text. Empty or missing summary renders as an em-dash. The prior-issue label resolves via a server-built `runLookup` from the full pre-paginated run list (`formatRunDateTime(endedAt ?? startedAt)` when matched, otherwise `run …<last6>`). Server-side parse keeps the runtime shared import off the client bundle, mirroring the failed-feeds boundary.
- **Feature 05 — Threshold env config:** Documents the threshold as a committed `.env.example` entry with a usage comment and a `README.md` section explaining default, range, `>=` semantics, no-GUI scope, and the worker-restart requirement for changes to take effect on the next run. A docs-guard test parses the repo root by walking up from `import.meta.url` to `pnpm-workspace.yaml` (not `process.cwd()`) so it works under `pnpm --filter`, and asserts both the example file and the README mention the key, default, and restart signal.
- **Feature 06 — Hardening review 2026-07-13:** Closed four findings from the stage code review. **S1**: symmetric empty-candidates short-circuit in `suppressCrossRunTopics` so an empty candidate pool skips all embedding work. **S2**: ten additional parser edge-case tests (`'0.85abc'`, `'NaN'`, `'Infinity'`, `'   '`, `Number.NaN`, `Number.POSITIVE_INFINITY`, `Number.NEGATIVE_INFINITY`, `'foo'`, `'  0.85  '`, `Number(-0)`) pin the contract against future refactors. **S3**: five malformed-embed-client tests (`makeMalformedEmbedClient`) exercise the `assertEmbeddings` length/shape/non-array/non-finite guards end-to-end through `suppressCrossRunTopics`, each reaching the no-op fallback without throwing. **S4**: `formatPriorIssueLabel` returns the literal `"unknown prior"` when `matchedRunId === ""`, so the cell no longer surfaces the misleading `"run …"` shape on synthetic data.
- **Feature 07 — Formatting maintenance:** Restored the repository-wide Prettier gate. `.prettierignore` adds the four intentional exclusions (`output/` generated archive, legacy `newsletters.yaml`, IDE-owned `.cursor/` and `.opencode/`) and nothing else. Every maintained file from the initial Prettier baseline is reformatted by the unchanged configuration; `pnpm format:check` exits zero with no `[warn]` file entries.

## Decisions and deviations

- **`lookback` update sentinel is `?? -1`, not `?? 0`.** Zero is a valid lookback (cross-run suppression off), so the update path must distinguish a missing form field from an explicit zero. The `?? -1` sentinel forces `validateLookback` to reject, surfacing the bug as a validation error rather than silently disabling suppression on save. The form's `required` attribute is the primary guard; the sentinel is defense in depth.
- **Suppress runs on the full scored array before MMR's `minScore` filter.** A candidate that MMR would have dropped for low score may still appear in the suppression record when its title+tags embedding is close to a prior topic. This keeps the operator's audit (which titles were suppressed and why) complete rather than partially hidden behind the score gate.
- **Empty pool after suppress fails the run with the same "No articles selected" message as today's empty MMR outcome.** Short-survivor runs (where suppress leaves fewer candidates than `newsItems` but more than zero) complete normally — under-target is not a failure. Only the genuine pool exhaustion is fatal, and the suppression record is persisted before the failure so the operator sees what happened.
- **Suppress embed uses title + tags; MMR survivors use title + body.** The two comparisons ask different questions: suppress asks "is this the same topic as something we already covered?" (topic-shape text), MMR asks "is this redundant within today's pool?" (full-article text). Locked decision; not user-facing.
- **No per-newsletter or soft-penalty threshold modes.** The threshold is global and the drop is hard. Per-newsletter lookback remains the only per-newsletter suppress knob in V1.
- **Hardening review (Feature 06) was optional but accepted.** The four fixes are narrow and defensive; the most consequential is S3 (the `assertEmbeddings` finiteness guards), because `execute-run.test.ts`'s `suppressFn` stub never drives the real `assertEmbeddings` path — without S3, malformed embeddings could silently short-circuit cosine with `>= threshold` quietly failing on `NaN`. The hardening covers the only path that per-feature tests would not catch.
- **Formatting maintenance (Feature 07) addresses a meta quality-gate concern.** No application code changed; the stage restored 171 baseline Prettier warnings to zero by formatting maintained files and adding four intentional ignore rules. Generated archives, legacy YAML, and IDE-owned directories are correctly excluded.
- **No deviations from any locked decision in features 01–05 or 06 hardening.** All locked constants (`DEFAULT_LOOKBACK = 3`, `LOOKBACK_MIN = 0`, `LOOKBACK_MAX = 10`, `DEFAULT_CROSS_RUN_SIMILARITY_THRESHOLD = 0.85`, `CROSS_RUN_SIMILARITY_THRESHOLD_ENV = "CROSS_RUN_SIMILARITY_THRESHOLD"`, ≥ comparison, three-letter "unknown prior" label) are present and enforced.

## Deferred and out of scope

Per the stage file, these remain for later stages or future directions:

- **LLM-as-judge for topic sameness** — embedding similarity is the V1 mechanism; a future direction once LLM cost/latency improves.
- **GUI control for the similarity threshold** — env-only in V1 by design.
- **Soft / score-penalty mode** — hard drop only.
- **Cross-newsletter suppression** — lookback is same-newsletter only.
- **Stage 06 full per-article and pipeline-decision inspection** — the Runs list summary is the audit surface until then.
- **Changing Stage 04 retention policy** — this stage consumes the existing three-completed-runs protected floor and `topicSummary` field as-is.
- **Per-article manual curation (pin/drop/reorder) and interest signal (thumbs)** — explicitly deferred from V1 in PRODUCT.md Future directions; cross-run dedup does not preclude them.
- **Per-newsletter threshold override** — global threshold only in V1.
- **`.env` hot-reload without worker restart** — out of scope; worker reads `.env` once at boot via `process.loadEnvFile`, compose injects `env_file` at container start. README documents the restart requirement.

None. The cross-run deduplication stage is closed and ready for Stage 06 (preview and inspection), which can build its full per-article / pipeline-decision inspector on top of the `suppressSummary` field this stage already persists on every run document.
