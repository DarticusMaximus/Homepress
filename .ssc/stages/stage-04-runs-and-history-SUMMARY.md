# Stage 04: Runs And History — Summary

## What this stage delivered

The operator can now generate newsletters from the GUI, watch each run progress through its phases, see what failed and why, retry a failed run without repeating any work it already finished, and notice when an RSS source is silently going dead — all without touching the CLI, the shell, or any logs.

On the Newsletters page, every definition now has a **Generate** button. While a run is in flight, the button shows **Generating…** and is disabled; a second click while one is already in flight is rejected at the server (you cannot accidentally start two runs for the same newsletter). The run is enqueued on a button click and the web request returns immediately — generation happens in the worker, not in the browser or in a Next.js callback.

There is now a **Runs** page at `/runs` showing every run with its newsletter name, start/end time, status, the phase that was in progress (or that failed), and — for failed runs — the failure message and a **Retry** button. Retrying a failed run picks up exactly where it left off: if the run got as far as `tag` before failing at `score`, retry starts at `score` and the completed fetch, scrape, and tag work is reused. The worker does **not** refetch any websites and does **not** call the LLM again for phases that already have durable checkpoints. Transient OpenRouter flakiness or a brief network blip is now recoverable in one click.

Feeds now carry an **operational health** signal alongside the qualification status from Stage 03. After three consecutive failed fetches of the same feed, the feed is marked unhealthy. After the next successful fetch, it returns to healthy. The Feeds page shows a Health badge for every feed, with a deep-linkable filter (`/feeds?health=unhealthy`) that survives pagination. The dashboard now shows a Feeds health indicator next to the database card: green when all feeds are healthy, red with the unhealthy count and a link to the filtered Feeds page when any are down. The Runs page also calls out runs that touched currently-unhealthy feeds, and runs that died with zero articles (the "all feeds are dead" case) now record exactly which feeds failed, so the most-affected run gets the most-affected view.

Finally, run history is now bounded. There is a small **Retention** control on the Runs page where the operator can change how many days of history to keep (default 30, range 1–365) and trigger an immediate cleanup. Cleanup is automatic on the worker too: a best-effort purge fires on boot and then once every 24 hours. Each newsletter's **three most recent completed runs are always preserved** even when older than the retention window, so the next stage's cross-run topic deduplication has a stable floor to work with.

## How it maps to the plan

- **Stage Intent:** Make newsletter generation observable and safely recoverable, so the operator can diagnose failures, retry without repeating completed network or LLM work, and notice feeds that have become unreliable. This makes the proven pipeline practical to operate through the GUI and serves the product's goal of reliable on-demand generation.
- **Acceptance criteria met:**
  - [x] Starting a manual run creates a visible run record; a newsletter cannot have two active runs simultaneously.
  - [x] Every successful pipeline phase leaves a durable checkpoint containing the full result required by later phases and a retry.
  - [x] A completed run and a failed run are distinguishable in history; failed runs show the phase and failure message.
  - [x] Retrying a failed run starts at its failed phase and does not repeat any completed phase's website requests or LLM calls.
  - [x] A feed becomes unhealthy after three consecutive failed fetches and becomes healthy again after a successful fetch.
  - [x] Feed management and affected run records identify unhealthy feeds; the dashboard shows a green feeds indicator when all are healthy, otherwise a red indicator with the unhealthy-feed count that links to feed management.
  - [x] The retention setting defaults to 30 days, removes eligible old run records, and never removes a newsletter's three latest completed runs.
- **North star link:** The product replaces a fragile CLI/YAML workflow with a GUI. Before this stage, even with feeds and newsletters configurable, the operator still had no way to actually generate an issue from the web app — and once they did run something, there was no record of what happened, no way to retry a transient failure without starting over, and no signal that a feed had gone quietly dead. This stage closes that gap: runs are observable, recoverable, and trustworthy, and Stage 05's cross-run topic deduplication now has the durable run history it needs to do its job.

## What was built

- **Feature 01 — Run checkpoints:** A new `runs` Appwrite collection with per-phase Storage files in a `run_checkpoints` bucket. Each successful pipeline phase (`fetch`, `scrape`, `tag`, `score`, `selection`, `draft`) saves its full result for the next phase into a JSON file in the bucket and records the file id on the run document; the document also carries `topicSummary` (selected-article titles + tags, written only on completion), `failedFeeds`, and lifecycle fields (`status`, `currentPhase`, `completedPhase`, `failedPhase`, `failureMessage`, `startedAt`, `endedAt`). Embeddings are stripped on `score` and `selection` writes so checkpoint files stay small and reversible. Schema-as-code only; bucket + collection + attributes are provisioned idempotently on worker boot.
- **Feature 02 — On-demand runs:** A web server action `startNewsletterRun` validates the newsletter is runnable (topics non-empty; ≥1 attached `ok` feed), enforces one-active-run-per-newsletter with a race-aware re-check that marks every concurrent start that lost the race as `failed`, then creates a `pending` run and returns immediately — no LLM work in the web process. A new worker poll loop claims `pending` runs FIFO and runs a **checkpointed executor** that calls each phase in order and saves the checkpoint after each success. Single in-flight run per worker process; SIGTERM best-effort marks an in-flight run `failed` so it can be retried. The Newsletters list shows a **Generate** button on every row/card that flips to disabled **Generating…** while an active run exists.
- **Feature 03 — Run history:** `/runs` page replaces the placeholder with a responsive table/cards list of every run, with newsletter, started/ended time, status badge, phase column (with status-specific display rules), failure message (failed runs only), and a **Retry** control (failed runs only). Pagination 20 per page; filter by newsletter and by status; filter params preserved across Prev/Next; empty state and load-error Alert match the established Feeds/Newsletters patterns. The Retry action is a contract shell with three locked guard strings (`"Run not found"`, `"Only failed runs can be retried"`, `"A run is already in progress for this newsletter"`) — all four outcomes covered by automated tests.
- **Feature 04 — Failed-run retry:** Retry now does the real work. It requeues the **same** run document as `pending` (no second row), preserving `completedPhase` and all checkpoint ids, then the worker's checkpointed executor resumes at the first incomplete phase. If the run failed at `score` after `tag` completed, retry re-uses the tag checkpoint and only re-runs `score`, `selection`, `draft`. The pre-flight checkpoint check refuses to retry if the prior checkpoint file is missing, with a locked error string. Race cleanup mirrors Feature 02. Selection-phase retries still re-embed (embeddings are not checkpointed by design — MMR selection needs them); score/tag/fetch/scrape LLM and network work are never repeated on retry. Hardening pass in Feature 07 added the resilience (ticking flag, idempotent shutdown, error-type-distinguishing catches, secret redaction, structured logging) so this path is production-safe.
- **Feature 05 — Feed health:** Four new `feeds` attributes (`operationalHealth`, `consecutiveFetchFailures`, `lastFetchError`, `lastFetchAt`) added via schema-as-code. `applyFeedFetchOutcomes` runs at the end of every fetch phase (including the all-feeds-dead zero-article fatal path) and updates the counter per feed URL; `unhealthy` flips at three consecutive failures, back to `healthy` on the next success. Qualification `status` is never touched by health updates (the two concerns stay isolated). UI: a Health badge on every Feeds row/card with a fetch-failure hint; a `?health=unhealthy` filter that survives pagination; the Runs page now shows Failed feeds and an **Unhealthy** badge on rows whose failed feeds are currently unhealthy; the dashboard Feeds card is green when count is 0 and red-with-count-and-link when any are unhealthy.
- **Feature 06 — Run retention:** A new singleton `app_settings` collection with `runRetentionDays` (default 30, range 1–365). The Runs page now has a compact **Retention** control: input + Save + **Clean up now**. A pure `selectRunsForDeletion` enforces the eligibility rules (never active runs; never a newsletter's three most recent completed runs). `purgeExpiredRuns` performs a pre-delete status re-check (guards against the same-document-retry race) and `deleteRun` cascade-deletes checkpoint Storage files before the document. The worker fires a best-effort purge on boot and then on a 24h interval, with single-flight and clean shutdown.
- **Feature 07 — Hardening review 2026-07-11:** Optional review pass closed 20 findings (worker poller race + idempotent shutdown; checkpoint-load error handling; retry + race-cleanup error isolation; executor data-loss prevention including `markCompleted` retry to preserve resumability; secret redaction in persisted failure messages; structured logging for execution traces; feeds-page filter UX; web observability for purge errors and Runs-page degradation; `RetentionControls` test coverage; accessibility labels on list actions; anti-cheat test hygiene; dashboard error leak; counter-assumption documentation). No architectural changes; each fix is localized.
- **Feature 08 — Remediation:** A stage-regression pass found that AC #6 ("affected run records identify unhealthy feeds") was failing for one specific path: a zero-article fetch (all feeds dead) marked the run `failed` at `fetch`, but `Run.failedFeeds` was never persisted — only the fetch-checkpoint save persisted `failedFeeds`, and the zero-article fatal path bypassed checkpointing. `markFailed` was extended with an optional `failedFeeds: FeedFailure[]` argument; the zero-article branch in `execute-run.ts` now passes `fetchResult.failedFeeds` through, so the Runs page can name the dead feeds on the very run that died because of them. Backwards-compatible with all other `markFailed` callers.

## Decisions and deviations

- **Stage 04 had its own regression-and-remediation cycle**, the first in the project. The cross-feature regression pass found that AC #6 failed for the zero-article fatal case (per-feature verifiers all passed; the gap was cross-feature). Rather than weakening the AC or silently fixing the gap, the verifier filed a remediation feature spec, ran it through `ssc-execute`, and re-finalized. The trail is preserved in `feature-08-remediation.md` and in the `ssc-state.json` escalation log.
- **Resume uses a requeue, not a new run.** Failed-run Retry updates the same `runId` rather than creating a new row. This keeps history meaningful (one row per operator intent) and keeps `startedAt` accurate. The remediation feature in `feature-08-remediation.md` then handled the same-document race (concurrent Retry + concurrent Generate) by mirroring Feature 02's race re-check pattern.
- **Retention default 30 / protect 3 are fixed in this stage** (per the Plan.md carry-forward pin). The protected count is not operator-configurable here because Stage 05's cross-run topic deduplication needs a stable floor to guarantee the lookback window. If we later want the operator to raise the floor, that becomes a Stage 05 feature change.
- **Pre-attach qualification (`status`) and run-time health (`operationalHealth`) are deliberately separate fields.** Stage 03 already owns the qualification gate; this stage adds a second axis without overloading the first. Unhealthy `ok` feeds are not auto-detached — the operator is alerted, not silently blocked.
- **Hardening review (Feature 07) was optional but accepted.** The PM chose to address all 20 findings before finalization. Most fixes are localized; the highest-impact cluster is execution-path error handling (`markCompleted` retry to preserve resumability is the single most important fix — without it, a transient `markCompleted` failure would leave a fully-completed run non-resumable).
- **The checkpoint-save-failure path** (where fetch succeeded but the Storage save itself failed) was **deliberately left out of scope** in the Feature 08 remediation. That case would also lose `failedFeeds` from the run document, but `applyFeedFetchOutcomes` already updated the feeds collection (the operator's primary signal). If it becomes a real issue in PM manual testing, it should be filed as a follow-up hardening spec rather than widening this remediation.
- **No deviations from any locked decision in features 01–06.** All locked constants (`FEED_UNHEALTHY_THRESHOLD = 3`, `DEFAULT_RUN_RETENTION_DAYS = 30`, `PROTECTED_COMPLETED_RUNS_PER_NEWSLETTER = 3`, `MIN = 1`, `MAX = 365`, `PHASE_ORDER = ["fetch","scrape","tag","score","selection","draft"]`, three locked Retry guard strings) are present and enforced.

## Deferred and out of scope

Per the stage file, these remain for later stages:

- Scheduled or batched execution and cross-newsletter concurrency policy → **Stage 08**
- Cancelling an in-progress run
- Detailed per-article and model-decision inspection → **Stage 06**
- Cross-run topic deduplication over a lookback window → **Stage 05** (this stage guarantees a floor of 3 completed runs per newsletter so Stage 05's lookback is stable)
- Per-newsletter retention configuration (floor stays at 3)
- Email/push alerts for feed health (in-app surfaces only)
- Per-feed health time-series history
- Appwrite TTL attributes or bucket lifecycle rules
- Soft-delete / undo for removed runs
- Per-row Delete on the Runs page
- Mobile app (responsive web is sufficient)

## Open questions for the next stage

- **Stage 05 inherits the protected-3 floor.** The cross-run topic dedup in Stage 05 reads from the run history this stage built. The eligibility rules in this stage guarantee that the three most recent completed runs per newsletter are never deleted, which is the minimum Stage 05 needs to suppress topic repetition across consecutive issues. If Stage 05 plans a different lookback default (e.g., last 5 issues) it must either keep the protected-3 floor and look further back, or grow the floor as a coordinated change. The Plan.md should be updated if either happens.
- **Stage 08 (scheduling) shares the worker transport** (the `runs` collection as a job queue). Stage 04's poller currently runs at a 3s default interval with one in-flight run per worker process. Stage 08 will need to think about cron-style triggers that create `pending` runs, cross-newsletter concurrency, and whether the 3s poll is still appropriate when there are scheduled jobs that need to fire on the minute.
- **The checkpoint-save-failure path** noted under "Decisions and deviations" is a small known gap. If PM manual testing reveals it happens in practice, file a follow-up hardening spec; otherwise leave it.
- **Selection-phase retries still re-embed** by design. If embedding cost or latency becomes a concern when retries are common, a future stage could persist embeddings on the score checkpoint and skip the re-embed on selection — but that would change Feature 01's checkpoint payload contract and is not on any roadmap today.
- **Carry-forward pin for the next stage:** the legacy Python system's lack of run history caused silent topic repetition across issues; Stage 05's success depends on Stage 04's run history being durable and queryable. This pin is already reflected in the Plan.md decision log.
