# Stage 01: Pipeline Engine — Summary

## What this stage delivered

The single riskiest assumption in the whole project — that a TypeScript rewrite can match the legacy Python pipeline's filtering quality — is now proven. Before this stage, the project could not be sure it was worth building a GUI, run history, scheduling, and delivery around an engine that might not actually produce a good newsletter. After this stage, the engine works, and every later stage is operability on top of working compute.

You now have a complete, headless filtering pipeline written entirely in TypeScript. Given a newsletter definition (a list of RSS feeds, the topics you care about, the topics you don't, an audience description, and how many items you want), it runs the full chain automatically: fetch every feed concurrently → scrape each article's real body from its web page → tag each article with broad topic tags via an LLM → score each article's relevance to your topics via an LLM → select the final set using a diversity algorithm (so you don't get five articles about the same thing) → draft a finished markdown newsletter via a high-reasoning LLM. The output is a readable newsletter with a featured item and per-item links, comparable in relevance, diversity, and readability to what the old Python pipeline produced on the same inputs. That comparability was judged by you, the operator, on a real day's feeds — the stage's defining test.

You can run the whole thing end-to-end with one command (`pnpm --filter worker parity-run worker/sample-newsletter.json`) against a sample newsletter config, with no GUI and no manual step-through. The engine is pure compute: it takes a config and returns a finished draft string. It writes nothing to a database — that comes in later stages.

A defining quality property of the engine is that it fails loudly rather than silently degrading. If an LLM starts returning blank or garbage responses, the consecutive-error halt trips after three in a row and stops the phase with a clear error, rather than quietly producing a worse newsletter. The same loud-failure contract applies across the tag, score, and draft phases. This matters because silent degradation was exactly the failure mode that made the legacy pipeline unreliable.

The stage also delivered a hardening pass (feature 08) that closed a full code review — 22 findings across security defense-in-depth (URL scheme validation, response body size caps, path-traversal guards), correctness (strict score parsing that catches blank LLM responses, finiteness guards on the embeddings used by the diversity algorithm), and maintainability (collapsed duplicate phase-name types, removed dead code, de-duplicated near-identical LLM-call paths). Two High correctness bugs were fixed: a blank LLM score response no longer silently scores zero, and a malformed embedding no longer silently corrupts article selection.

## How it maps to the plan

- **Stage Intent:** "Prove the riskiest assumption in the whole project: that a TypeScript pipeline can match the legacy Python pipeline's filtering quality end-to-end. Every later stage is wasted scaffolding around an engine that doesn't work — so the engine is proven headless, via a test harness, before any UI is built. If this stage fails, the project pivots; if it succeeds, the core value (condense the firehose to a relevant digest) is real and the rest of the product is just operability on top of it."
- **Acceptance criteria met:**
  - [x] The pipeline runs end-to-end from a newsletter definition to a finished markdown draft via a single test-harness command (`worker/src/parity-run.ts`), with no GUI and no manual phase stepping.
  - [x] Fetch phase: all feeds attempted; a dead/unreachable feed is reported as a per-feed failure and does not abort the run; articles outside the configured date range are excluded.
  - [x] Scrape phase: extracted content is non-empty main-body markdown; when extraction fails or returns nothing, the RSS summary is used as fallback.
  - [x] Tag phase: every article reaching tagging comes out with a tag list (possibly empty on per-article failure); 3 consecutive tagging failures halt the phase with a clear error.
  - [x] Score phase: every tagged article receives a numeric score in [0, 10]; 3 consecutive scoring failures halt the phase with a clear error.
  - [x] MMR phase: selection returns exactly the configured item count (or fewer if the candidate pool is smaller) and is observably more topically diverse than naive top-N-by-score.
  - [x] Draft phase: the drafter produces a non-empty markdown newsletter with a distinct featured item and per-item links.
  - [x] **Parity check (defining criterion):** on the same newsletter definition and the same day's feeds, the TS pipeline's output is judged by the operator to be comparable in relevance, diversity, and readability to the legacy Python pipeline's output.
  - [x] All LLM-calling phases route through OpenRouter using `.env` credentials and per-component model names (overridable via env, with legacy defaults preserved).
  - [x] No persistence, no run records, no Appwrite writes — the engine is pure compute that takes a config and returns a draft string.
- **North star link:** This stage delivers the product's first Goal (condense and filter the firehose to a relevant digest) and its core non-GUI capability. The PRODUCT.md success criterion "Newsletter output quality matches or exceeds the current Python pipeline on the same inputs" is now met for the headless engine. Everything the PRODUCT.md describes about managing, scheduling, previewing, and delivering newsletters is what the remaining stages build on top of this proven engine.

## What was built

- **Feature 01 — Pipeline types & config model:** The shared TypeScript vocabulary (article, tagged article, scored article, selected article, newsletter config, per-phase results) every other feature imports, plus the config helpers carrying the legacy model defaults, score threshold, and date-range logic. The data shapes that stage 02 will later persist to Appwrite were defined here first, so the engine is self-describing without a UI.
- **Feature 02 — RSS fetcher:** Concurrent fetch of a feed list, RSS/Atom parsing, date-range filtering, per-feed error isolation (one dead feed doesn't sink the run), structured per-feed failure reporting, and cross-feed deduplication so the same article syndicated across two feeds isn't processed twice.
- **Feature 03 — Article scraper:** Extracts article main content as cleaned markdown from a URL using Mozilla Readability + jsdom + turndown — pure TypeScript, in-process, no Python sidecar. Falls back to the RSS summary whenever extraction fails or yields too little real content, and never throws, so the rest of the pipeline is never broken by a bad scrape.
- **Feature 04 — Tagger (+ shared LLM client):** The first LLM phase — calls the tagger model per article to produce up to ten broad tags, with retry + exponential backoff and a consecutive-error halt. This feature also built the shared OpenRouter client and the reusable retry helper that the scorer and drafter reuse unchanged.
- **Feature 05 — Scorer:** The second LLM phase — calls the scorer model per tagged article to produce a 0–10 relevance score against your topics and disliked topics, parses and clamps the numeric response, and shares the tagger's retry/backoff/halt contract.
- **Feature 06 — MMR diversity selection:** Embeds each score-passing article via the embedding model, then selects the final set using Maximal Marginal Relevance (λ=0.5) so the result is both relevant and topically diverse — not just the N highest-scored articles.
- **Feature 07 — Drafter + orchestrator + harness:** The capstone — the drafter LLM turns the diverse selection into a finished markdown newsletter; the orchestrator wires all six phases into one runnable chain returning a structured result; and the CLI harness runs the full real chain against live RSS + OpenRouter so parity with the Python pipeline can be judged side-by-side.
- **Feature 08 — Hardening review:** Closed all 22 findings from the stage code review (0 Blocker, 2 High, 20 Medium): strict score parsing (blank/garbage LLM responses no longer silently score zero), embedding finiteness guards (a malformed vector no longer corrupts selection), URL scheme/body-size/path-traversal defense-in-depth at every untrusted-input surface, fail-fast retry on permanent 4xx errors, and a cleaner type surface. A post-verification correction introduced a distinct raw-fetch byte cap (5 MB) separate from the prompt-truncation cap (70 KB), after the original hardening spec conflated the two and caused the scraper to fall back to short RSS summaries on ~90% of articles; the corrected parity run extracts 93% of articles.

## Decisions and deviations

- **Scraper engine swap, documented.** The legacy pipeline used Python's `trafilatura` for main-content extraction. No faithful TypeScript port exists, and the available JS/TS options (notably `@mozilla/readability`) are noticeably weaker heuristics. The original plan compromised on a Python sidecar HTTP service for fidelity. During execution this was reversed: the scraper was rewritten as pure TypeScript (Mozilla Readability + jsdom + turndown, in-process, no second container) — a deliberate trade against fidelity-for-purity to keep the deployed system Python-free. The extraction engine differs from trafilatura, so the claim is comparable-purpose extraction, not byte-identical parity; the stage's operator-judged parity check is the safety net, and it passed.
- **cleanContent is a modified port, not a faithful one.** The cleaning step preserves markdown-link URLs that the legacy `_clean_content` destroyed, plus a sentinel-leak guard. This was surfaced as spec drift in the code review and resolved by amending the feature-03 spec to "modified port" and documenting the actual behavior. End-result quality is what parity validates, not byte-identical cleaning.
- **Cosine similarity instead of raw dot product in MMR.** The legacy used raw dot product (silently assuming the embedding model returns unit-normalized vectors). The TS port uses proper cosine similarity — textbook-correct MMR independent of the model's normalization. Selection sets may differ slightly from the legacy run; this is expected and was accepted by the parity judgment.
- **Structured phase results instead of raising on halt.** The legacy tagger/scorer raised an exception on the consecutive-error halt, losing the partial result. The TS port returns a structured result with a `halted` flag — same loud-fail contract, but partial state is preserved. This was done deliberately to feed stage 03's resume-from-last-phase capability.
- **No inter-phase delay.** The legacy waited between phases to respect rate limits. The TS pipeline drops this — OpenRouter's rate limits don't require it. The `interPhaseDelaySeconds` config field is accepted but ignored.
- **`not-selected` failure category added (C7).** The carried-forward pin noted that the selection accounting invariant only held when the requested item count was at least as large as the candidate pool. The hardening pass added a `not-selected` failure reason so every scored article is accounted for universally — a prerequisite for accurate stage-03 run records.
- **Two-layer byte cap, not one.** The P1 hardening finding conflated two unrelated limits by name. The post-verification correction introduced `DEFAULT_MAX_FETCH_BYTES` (5 MB, a DoS guard on the raw HTTP response body) distinct from `DEFAULT_MAX_CONTENT_LENGTH` (70 KB, the prompt-truncation budget on cleaned article text). The lesson — reference constants by purpose and units, not just identifier — is recorded in the feature-08 spec for future spec authors.
- **Code review run before finalize, all findings hardened.** An `ssc-code-review` pass surfaced 0 Blockers, 2 High, 20 Medium findings; a hardening feature spec addressed all 22 before this stage gate. The two High bugs (silent zero-score on blank LLM responses; NaN-corrupted selection on malformed embeddings) would have undermined the stage's defining parity claim by allowing silent degradation — both are demonstrably fixed.

## Deferred and out of scope

Per the stage's Out-of-scope section, the following were intentionally left for later stages and remain open:
- **Appwrite persistence** (run records, intermediate phase state, newsletter definitions) — stage 03.
- **Resume-from-checkpoint / resume-from-last-phase** — stage 03 (the structured `halted` results built here are the foundation for it).
- **Cross-run topic deduplication (temporal diversity)** — stage 04.
- **GUI, run triggers, run history, scheduling** — stages 02–07.
- **Email / RSS-feed / export delivery** — stage 08.
- **Prompt template editing** — the legacy prompts were ported verbatim as constants; making them editable is stage 06.
- **Per-newsletter model overrides through a UI** — defaults + env overrides only here; GUI overrides are stage 06.

The carried-forward pin from this stage (the `SelectionResult.failures` invariant and the `not-selected` category) is now resolved in code; stage 03 should still consider surfacing a `not-selected` telemetry category in its run-record design so the accounting is visible to the operator, not just structurally correct.

## Open questions for the next stage

- **Selection telemetry in run records.** The `not-selected` failure category now makes the accounting invariant hold universally (feature 08, C7). Stage 03 (runs-and-history) should surface this in the run-record UI so the operator can see how many above-threshold articles were considered but not selected — not just rely on the invariant being structurally correct.
- **`SelectionFailure.reason` as an open enum.** The reason union is now `'below-threshold' | 'embedding-failed' | 'not-selected'`. Stage 03 may discover additional categories worth recording (e.g. a dedup-hit category once cross-run suppression lands in stage 04). The type is additive, so this is a note, not a blocker.
- **Parse-failure rate of the nemotron scorer.** Feature 05 deliberately strengthened the contract so a non-numeric scorer response counts toward the consecutive-error halt (legacy treated it as benign). The parity run did not surface nuisance halts from this, but stage 06 may want to surface a "parse failures don't count" toggle if real-world scorer reliability proves marginal.
- **Embedding reuse.** Feature 06 dropped the legacy in-memory embedding cache as dead weight (each candidate is embedded once per run). Stage 04 (cross-run deduplication) should revisit whether a persistent embedding store earns its keep once run history is retained.
